# 下载规划器：范围合并、切片与文件间调度

Status: proposed

## Problem

[下载合并](../../../native/session/merge.rs)通过增加少量传输字节减少请求数量；小文件使用合并全量请求，即使存在补丁，也可能比独立请求补丁更快。这是需要保留的性能取舍。文件获取同时受请求数量、节点分布、压缩数据量、解码开销和磁盘速度影响，不能只按补丁大小选择方案。

[当前执行器](../../../native/session/run.rs)按大任务 5、小任务 11、本地任务 16 限制并发。单个大文件仍对应一个下载流，其他任务完成后可能成为最后一个长时间运行的任务。直接在每个文件内部增加并发，又会使实际请求数乘以切片数量，并让少数大文件占满下载名额。

[builder 分类](../../../native/builder/gen.rs)按原文件大小 1MiB 区分大、小文件，将未变化的小文件、变化或新增的小文件、小补丁和大补丁分别归类。[打包排序](../../../native/builder/pack.rs)按分类顺序和内容名称排列，形成较连续的更新数据区域。客户端当前按 500KiB 接纳小文件、按包内偏移贪心合并，最大合并范围 10MiB、额外字节比例不超过 20%。包内 metadata 清除了 `packing_info`，规划器应利用实际索引位置，不能依赖分类信息随包传递。

DFS 调度器接受资源内部的任意合法 range。服务端可以建议切片大小和并发，客户端需要将这些建议用于统一规划，并处理切片乱序、临时落盘、范围重试和整文件回退。服务端建议描述运行时调度，不改变生产包格式。

## Proposal

### 范围与约束

规划器负责应用文件及补丁的获取、范围合并和切片，执行器负责请求调度、顺序供给解码器、校验与收尾。提交继续采用[文件提交协议](../implemented/2026-09-02-atomic-file-commit.md)。运行库和 Mirror酱 归档保持各自的业务流程，不因引入规划器而改写；它们继续接入共同的网络统计。

builder 的分类、条目顺序、压缩数据、索引编码及 metadata 写出方式保持不变。等效输入的产物除安装器本体及其长度导致的既有偏移变化外保持等效，新包仍能被基准版本 `ae461aa9ddd5a8f5e445459e14f5d611921f9938` 读取。切片仅划分已有压缩字节，不重新压缩、不插入分帧信息。

规划与执行使用内部类型，不向包 metadata 添加字段。前端和 native 同版本交付，私有 IPC 可以直接调整。提案中的具体参数是实现起点，性能测量后可调整；算法约束和失败语义需要稳定。

### 服务端建议和本地默认值

建议通过 DFS metadata 响应头提供以下字段，名称为拟定的协议名称，值均为十进制整数。大小字段的单位为字节，文中 MiB 表示 1024 × 1024 字节。

| Header | 含义 | 无建议时的拟定值 |
|---|---|---|
| `Dfs-Max-Part-Bytes` | 分片模式的单片上限；整文件单流回退允许超过它 | 50MiB |
| `Dfs-Preferred-Part-Upper-Bytes` | 大文件均分时的目标下界，优先得到介于此值与切片上限之间的切片 | 25MiB |
| `Dfs-Preferred-Part-Lower-Bytes` | 小文件组包的目标上界；切片均分时也尽量避免小于此值 | 10MiB |
| `Dfs-Download-Concurrency` | 本次下载会话建议的总在途数据请求数 | 16，按大任务 5、小任务 11 分配 |

25MiB 是默认切片目标。50MiB 取两倍目标作为初始切片上限；10MiB 延续现有组包规模作为初始合并目标。服务端的 50MiB、25MiB、15MiB 示例可覆盖这些值。文件是否适合参与合并、可接受的额外字节比例、预取资源上限由客户端决定，不通过 header 下发“合并下限”。

三个大小字段作为一组生效，要求完整且满足 `0 < lower <= upper <= max`；缺失、无法解析或顺序不合法时使用整组默认值。并发建议独立解析。客户端对建议值应用资源限制，拟定单片最大 256MiB、总请求并发最大 16；不允许服务端建议突破本地磁盘和并发预算。对于合法但过大的大小建议，等比例缩小三个值以保留相对关系；若缩放后的切片会低于客户端 1MiB 的最小切片目标，则使用默认大小组。客户端最小切片目标不限制独立小文件或无法合并的尾组。

建议值按会话固定。只读取所选 DFS 控制接口的响应头，不把任意下载节点响应头作为会话策略。现有 [DFS metadata 请求](../../../native/dfs.rs)需要在消费响应体前读取建议头，并把结果与 metadata 一起交给会话。形成范围清单后再创建 DFS2 会话，保持现有申报顺序；不为获取建议增加额外请求，也不在传输中因建议变化重分片。

### 规划结果与执行状态

文件、压缩数据和 HTTP 请求分别建模。文件有一个最终路径和校验目标；压缩数据指包中的完整文件内容或补丁内容；HTTP 请求可以覆盖多个数据项，也可以只覆盖一个数据项的一部分。下列结构表达主要关系，沿用现有路径、哈希和来源类型，不作为包内序列化结构。

```rust
struct SizeHints {
    max_part_bytes: u64,
    preferred_upper_bytes: u64,
    preferred_lower_bytes: u64,
}

struct DownloadPolicy {
    sizes: SizeHints,
    large_requests: usize,
    small_requests: usize,
    local_workers: usize,
    prefetch_parts_per_file: usize,
    prefetch_disk_bytes: u64,
}

enum Materialize {
    Embedded { entry: usize },
    Full { payload: usize },
    DiskPatch { base: usize, delta: usize },
    HybridPatch { embedded_base: usize, delta: usize },
}

enum DecodeKind {
    Zstd,
    Raw,
}

struct PlannedFile {
    metadata_index: usize,
    materialize: Materialize,
    full_fallback: Option<usize>,
}

struct Payload {
    source_object: usize,
    offset: u64,
    len: u64,
    decode: DecodeKind,
}

struct RequestSpan {
    source_object: usize,
    offset: u64,
    len: u64,
}

enum Transfer {
    Single { payload: usize },
    Merged { span: RequestSpan, payloads: Vec<usize> },
    Sliced { payload: usize, spans: Vec<RequestSpan> },
}

struct DownloadPlan {
    files: Vec<PlannedFile>,
    payloads: Vec<Payload>,
    transfers: Vec<Transfer>,
    policy: DownloadPolicy,
}
```

`source_object` 标识同一次安装选定的资源和版本，也可指向本地内嵌数据；`offset`、`len` 表示压缩数据或未压缩安装器映像的实际范围。只有远端 payload 进入 `transfers`，纯离线计划不解析节点、不申报 range。`DecodeKind` 只区分已有的数据解码方式。计划不保存临时签名 URL，URL 在派发或重试时解析。内部使用 `u64` 做范围计算，转换成现有包索引宽度或平台类型时检查边界。

对于相同压缩数据服务多个目标路径的情况，计划保留每个目标的生成与校验任务。可以复用 payload 描述，但不能仅因范围相同而合并成一个只能消费一次的流；首个实现允许重复读取，不引入跨文件缓存或硬链接。

传输状态单独记录每个请求的尝试次数、每个文件是否已向解码器供给数据、已完成文件和回退状态。状态不回写不可变计划。每个目标文件只记录一次最终完成；取消、原始失败与连带停止遵守[重构审阅修复提案](./2026-09-20-refactor-review-fixes.md)。

### 利用包内排列选择生成方案

规划从当前安装实际需要的文件出发，排除跳过项。内嵌完整文件优先直接读取；可用的内嵌基文件加补丁继续保留为候选。磁盘补丁必须匹配扫描得到的基文件哈希，不能仅凭存在目标补丁就标记为可用。

合并候选的原文件大小上限拟定为 1MiB，与 builder 的小文件分类一致。该值控制哪些文件可以为了减少请求而选择合并全量；传输组大小、切片大小和额外字节均使用索引中的实际压缩长度。参与合并不要求携带 `packing_info`，也不推断某段哈希名称属于哪个分类。

2MiB 作为生成器与客户端协同调整的实验候选。只提高客户端资格上限可以合并已有布局中相邻的 1MiB～2MiB 文件，但不能让生成器把这些文件按更新状态聚在一起；只提高生成器阈值则可能使客户端不接纳的文件夹在合并区域中，增加间隔传输和独立请求。正式采用协同调整会改变数据项顺序，必须同时处理本提案的 builder 产物等效约束；本提案中的虚拟布局实验不修改生成器或包文件。

对于适合合并且需要远端数据的小文件，先按完整目标数据的位置形成候选组；一个组至少包含两个不同且不重叠的数据项。对同一组目标比较两种方案：合并完整数据，以及采用有效补丁后按补丁和剩余完整数据的位置组包。两种方案都必须满足相同的范围与额外字节约束。请求数和压缩传输量都不更差的方案优先；两者存在冲突时，对这些小文件继续优先减少请求。请求数相同则选择传输字节更少的方案，完全相同则保持稳定的原候选顺序。

这一比较限定在完整数据候选组内，不搜索所有文件的组合。内嵌完整内容不参加远端全量方案；内嵌基文件补丁不为凑全量组而改为完整下载。没有形成完整数据组的文件按有效的本地、补丁、完整数据候选选择。选定后保留已有组，仅对尚未成组的小补丁再做一次按偏移组包，不重新搜索文件生成方式。由此可以利用“变化的小文件”和“小补丁”各自的连续排列，同时保留减少请求的既有偏好。

当前全量与补丁之间缺少经过测量的统一时间成本模型。这里明确采用有界的局部比较，不给每次请求虚构固定毫秒成本；基准验收要包含“极小补丁与较大全量组”的情况，确认减少请求的收益没有被额外传输和补丁处理成本抵消。

### 合并连续范围与均衡尾组

每个来源对象独立按包内偏移排序。合并只覆盖同一个对象、同一版本上的完整数据项，不把大文件切片与邻近小文件混进同一请求。组内的 TLV 头、未选中的数据及其他间隔都计入额外字节。

沿用 `额外字节 / 请求范围总字节 <= 20%` 的约束。超过该比例时结束当前组；尾组不足目标大小可以单独请求，不为达到建议值跨越大段未变化内容。这样 builder 聚在一起的实际更新文件自然形成较少的请求，而其他版本产生的不同更新集合也能按真实间隔处理。

组包采用按偏移扫描和一次相邻组边界调整。扫描时以 `lower` 为目标，在完整数据项边界停止；加入单个数据项导致超过目标时可以扩展到 `upper`，前提是额外字节比例仍合法。独立数据项大于 `upper` 时不为合并而切断，交给单文件或切片规划。

相邻两组使用前缀长度统计比较有限的分界候选：现有分界、最接近各半的位置、最接近 `lower` 的位置及这些位置相邻的数据项边界。保持两组时，分界移动不得增加总传输字节，两组都要保持不超过 `upper` 和 20% 的额外字节约束；在这些条件下优先改善最小一组的大小，再减少最大一组的大小。若两组总范围已能在 `lower` 内合法合并，则合为一组，此时允许在 20% 约束内多传间隔，以减少一个请求。该规则也允许后面的密集数据补足短前缀的占比，避免仅因最初遇到间隔就永久失去合并机会。

每个相邻边界最多调整一次，采用固定的并列裁定。前缀数据在全部有序项上建立一次，分组只保存边界下标；连续合并时不反复复制逐渐变大的组，也不重新计算组内总长度。重叠的相同内容引用保留独立消费关系，不跨越重叠边界做均衡。不使用反复迭代或全局动态规划。

例如，在数据连续、文件边界允许且额外字节合法时，目标 15MiB 的 26MiB 数据可形成约 13MiB＋13MiB，避免形成一个接近 25MiB 的组和一个 1MiB 尾组。大小均衡让不同请求的结束时间更接近，但不为填满并发名额而把已合并的小文件重新拆成大量短请求。

排序成本为 `O(n log n)`，扫描为 `O(n)`，边界调整通过前缀统计和二分定位有限候选。完整数据与补丁候选比较复用这些函数，避免对每个文件重新扫描全部 metadata、索引和补丁清单。

### 大文件按压缩范围均分

对于已知压缩长度 `B`、支持合法子范围请求的数据项，采用 `n = max(1, ceil(B / max), floor(B / upper))` 作为初始切片数。把 `B` 按整数除法和余数均分为 `n` 个连续范围，各片相差最多一个字节。`n == 1` 时保持单请求，不建立切片临时文件。`max` 是分片请求上限；均分受该上限约束而无法达到 `lower` 时，接受小于推荐值的切片，不扩大请求越过上限。

以 `max=50MiB, upper=25MiB, lower=15MiB` 为例，100MiB 分四片、110MiB 分四片、60MiB 分两片。大小为 49MiB 的数据可以保持单请求，50MiB 则形成两片。推荐值决定优化方向，不能保证阈值两侧的最优时间连续；这一边界属于调参比较项。

所有范围以源对象的实际偏移申报，覆盖原数据项恰好一次，不重叠、不遗漏，也不超出源对象边界。HTTP 的闭区间结束位置仅在发请求时计算。数据项长度未知或来源不支持可靠范围请求时保留已有单流路径，不为每个小文件额外发 HEAD 请求。

分片、合并和整文件回退的范围在 DFS2 会话创建时一起申报并去重。只为即将派发的请求获取 URL，分批解析有限的待运行范围，不一次预取全部切片和回退 URL。获取节点仍使用同一资源版本；同一文件的不同切片允许分配给不同节点。无论节点如何分配，范围响应必须核对状态、实际范围和长度，最终文件仍执行已有哈希校验。范围读取要求包内压缩字节保持原样，不能将额外 HTTP 内容解码后的偏移当作包内偏移；不能提供这一保证的来源使用已有整文件单流路径。

### 大、小任务和文件间公平调度

默认保留大请求 5、小请求 11、本地处理 16。大、小分类在切片前完成，初始沿用[现有大小分界算法](../../../native/session/run.rs)对逻辑传输任务分类；同一大文件的所有切片继承该分类。合并请求视为一个逻辑任务。服务端总并发建议为 `N >= 2` 时，大请求预算取 `clamp(floor(5N/16), 1, N-1)`，其余分配给小请求；`N == 1` 时在两个非空队列间轮转，避免长期饿死任一类。

每类同时处理的逻辑任务数不超过该类名额。名额优先让不同任务获得第一个请求，再分配额外切片；活动任务中优先考虑解码器当前需要的范围，然后按文件轮转发放预取名额。两个大文件共享 5 个名额时可以得到 3＋2；五个大文件则先各得一个。保留较大逻辑任务优先开始的顺序以减少收尾时间，但已开始文件之间按轮转分配，不能让一个文件连续取得所有后续名额。

可选调度方案是将上述分类名额作为保留额度，允许另一类借用没有任务可发的额度，总在途请求仍不超过会话并发上限。借用仍遵守不同文件优先、单文件预取限制和全局磁盘预算；借出的额度随请求完成归还，不为归还额度取消在途请求。该候选需要与固定分类预算对照验收，尤其检查小任务重新可运行时是否及时获得保留额度。网络模型中的静态队列不能验证解码或磁盘背压造成的可运行状态变化。

网络名额只覆盖等待派发的数据请求和响应体读取，释放不以整文件解码、校验或刷盘结束为条件。来源解析使用有限批次，不放开无限待解析队列。活动任务和预取预算独立限制尚未处理完的数据，避免网络名额释放后不断开启新文件导致暂存无限增长。网络混合补丁同时消耗网络名额与有界的处理能力，不能作为“本地任务”绕过网络预算。

拟定每个文件最多提前准备两片、整个下载执行器最多保留 256MiB 预取数据；写入前按完整切片大小预留磁盘预算，读完并删除后释放。纯本地处理保留 16 个任务名额；带网络任务的解码和补丁处理随各类活动逻辑任务上限受限，多个切片共用一个解码器，不按切片数增加处理任务。两类网络名额初始不互相借用，后续只在测量证明收益后考虑队列清空时借用空闲额度。

### 第一片流式处理与后续切片落盘

每个分片文件的第一片直接交给现有 Zstd 或补丁输入流。后续切片写到 `<staging>/dl/` 下由文件标识和片序号确定的临时文件，收完并核对范围长度后标记可读。解码器按片序读取，读完即删除；不能读取仍在写入的预取片。流保持连续，现有压缩帧和补丁格式不变。

后续切片采用固定落盘策略，不在同一实现中增加内存缓存转磁盘逻辑。第一片使用有界流缓冲；其他片额外付出压缩数据的一次写入和读取。预取临时文件不逐片 `sync_all`，它们不进入提交 journal，也不作为跨会话恢复缓存；最终产出文件继续校验和刷盘。可用空间检查包括已有暂存需求和实际可用的预取预算，不能只估算解压后的输出。

防止预取占满磁盘预算后阻塞解码器所需的下一片：已经具备所需片时优先消费；所需片尚未派发且无法预留完整空间时，允许该片像第一片一样直接流式供给，暂停更远的预取。调度器不得让所有名额都等待额外预取空间。取消或回退会唤醒等待临时文件的读取方，让阻塞补丁任务退出，并等待全部写入结束后清理。

### 范围重试和整文件回退

分片失败按其是否已向解码器提供字节处理。尚未供给任何字节的片，第一次可重试的下载错误删除该片的不完整临时文件，重新解析节点并完整重试该 range 一次；同一片第二次失败，使所属文件退出分片模式。已经向解码器供给字节后发生输入错误、解码错误或最终内容校验失败，直接退出分片模式。磁盘满、权限错误和用户取消不通过重新下载处理。

回退只影响所属文件。停止并等待它的其他切片和解码任务，删除该文件的临时切片与不完整输出，然后用一个请求获取完整目标文件并从头生成输出。回退请求可超过 `max`，仍占所属类别的一个网络名额。对于原方案是补丁的文件，回退获取完整目标数据，不再次尝试补丁。回退路径最多尝试两次，之后返回原始有意义的失败；不能重新进入分片或合并模式，也不能再套用 `install_one` 的三次外层循环。

普通合并请求在向任何文件解码器提供字节之前失败时，可重新解析并重试相同范围一次；一旦已开始供给，则保留已经完成校验的成员，未完成成员按各自整文件回退处理。已经成功的成员不重新下载、不重复计入完成量。普通单文件请求也使用同一个有限重试状态，替换分散在执行入口的嵌套循环。

### 会话与提权执行的分工

会话持有来源配置、DFS 会话、插件宿主和不可变下载计划；一个下载执行器持有该计划的所有任务、范围预算、解码器和临时文件。无需提权时在本进程运行，需要提权时整体运行在现有 helper 中，保证大、小名额和预取预算在同一处计算。

私有 IPC 增加一次计划执行及其取消操作，执行侧按需发送带计划标识与批次标识的范围 URL 请求，会话通过现有来源解析器回应。消息只传范围、URL、进度和结果，压缩数据与临时文件读取不经 IPC 转发。重试时可以重新请求节点，不把开始执行时取得的签名 URL 固定到结束。直接模式和提权模式复用同一解析接口，直接模式采用进程内调用。

会话结束或取消时，先停止范围解析与派发，并使待解析请求得到终止结果，再等待执行器中的网络、落盘和本地 blocking 任务结束。执行器完成后才能结束 DFS 会话、丢弃暂存目录或进入提交。计划执行取消属于本次下载任务的生命周期，不引入面向任意 IPC 操作的通用逐请求取消系统。

### 进度与诊断

UI 的文件总数和完成量按目标文件统计，切片数量不改变安装文件数。活动状态可以表达同一文件正在下载、解压或重试，但不把每个切片变成前端文件条目。具体展示结构沿用[过程信息展示对齐](./2026-09-21-progress-information-parity.md)。

实际网络接收量按请求尝试累计，包含失败尝试、重试、合并间隔和整文件回退。请求计数在执行器内汇总为计划操作的单调累计值，再通过已有进度通道发布，读取临时切片不再次计入网络量。各尝试的 range、耗时、字节和结果用于 DFS insight；速率采样和离线语义沿用[网络速度提案](./2026-09-21-network-speed-and-offline-progress.md)。

规划摘要记录有效建议值、逻辑文件数、初始请求数、预计压缩字节、合并额外字节和切片数量。执行摘要追加实际请求数、接收字节、回退数量、预取峰值和总耗时，便于判断减少请求是否实际改善性能。日志不写签名 URL 的敏感参数，不增加每次读取一次的 IPC 消息。

## Alternatives considered

- 保留全部现有参数，仅让大文件自行开启多个请求：会使文件并发与切片并发相乘，无法保证文件间分配和服务端总预算。需要统一执行器。
- 对每个文件先固定最省字节的生成方式，再做合并：可能把连续全量组变成大量零散补丁请求。先比较小文件组的两类候选，再固定生成方案，可以保留减少请求的已有收益。
- 使用全局耗时成本模型选择所有补丁、全量、切片和组包组合：需要可靠的节点吞吐、建连和本地解码成本估计，且计算和维护成本较高。有界局部比较及代表性测量更适合作为起点。
- 客户端重新读取或补发 builder 的分类信息：包内已清除该字段，而实际偏移足以利用现有排列。增加包字段会扩大兼容性工作且不改善实际布局。
- 全部切片缓存于内存：节点速度不均时内存占用较高；严格背压又可能限制预取收益。固定落盘提供明确资源上限，第一片直供保留下载与解码重叠。
- 下载完整压缩文件后再解码：实现更简单，但第一片也要落盘，且解码不能及时开始。顺序流适配器保留现有解码器。
- 每个切片边接收边供给解码器并支持任意中途续传：可以减少落盘等待，但片级重试需要维护精确消费位置。只对未供给字节的片重试，已经供给的失败转整文件回退，失败状态更少。
- 引入 `multipart/byteranges` 响应：多个独立 Range 请求已经可以利用不同节点，不需要恢复[已移除的 multipart 解析器](../implemented/2026-08-28-drop-multipart-download.md)。
- 安装过程中持续接受新建议并重分片：增加范围申报、在途任务和临时数据处理的状态。会话开始时固定建议能先验证主要收益。

## Acceptance criteria

### 必须保留的回归测试

测试集中在计划覆盖、资源上限和失败后数据正确性；复用既有来源、进度和提交夹具，不为每种来源、大小和并发组合建立 e2e 矩阵。

| 要测试什么 | 必须成立的结果 | 验证方式 |
|---|---|---|
| 建议缺失、错误、顺序不合法、合法覆盖和客户端资源截断 | 得到确定的有效策略；默认切片目标为 25MiB；有效策略不突破本地预算 | 一组表驱动解析与策略单测 |
| 非零包偏移、整除与余数、阈值边界、接近现有索引上界 | 切片恰好覆盖数据项，长度为正、不重叠、不越界，分片上限成立，整文件回退允许超限 | 范围算术单测，只计算整数，不分配对应大文件 |
| builder 式连续更新区域、变化小文件中 500KiB～1MiB 项、夹杂未更新内容和小补丁区域 | 使用实际偏移组包，额外比例受限；补丁与全量取舍遵守明确规则；结果稳定且目标文件无遗漏 | 小型合成索引与计划单测，覆盖两个局部候选及尾组均衡 |
| 纯内嵌安装、混合补丁、长度未知的来源、相同 payload 对应多个目标路径 | 离线不产生网络操作；混合处理计入实际网络预算；不适合切片的来源使用单流；每个目标都完成校验 | 复用计划与来源能力夹具，按有区别的路径各取一个输入 |
| 两个与五个大文件、大量小任务、一个请求名额、预取阻塞 | 大小预算和总预算成立；不同活动文件先获得名额；切片不改变分类；无无限抢占和空间等待死锁 | 可控执行器测试，不依赖墙钟速度 |
| 第一片直接读取、后续片乱序完成、当前所需片因预算不足改为直供 | 按原字节顺序解码，未完成临时片不可读，预取磁盘上限成立，读完释放文件 | 小型真实 Zstd 数据及临时目录测试 |
| 未消费切片第一次和第二次失败、已消费片失败、解码与最终校验失败 | 片级重试次数正确；只回退所属文件；重建输出和解码器；单流回退不再进入分片 | 同一故障注入夹具覆盖状态转移，核对最终文件内容 |
| 合并请求部分成员成功后失败 | 成功成员保留且只完成一次；其他成员走有界回退 | 复用流式合并夹具 |
| 本地与提权执行器取消、等待 URL 时取消、blocking 补丁仍在运行 | 等所有写入与解析等待结束后清理，原始错误不被连带停止覆盖 | 复用取消修复的执行上下文测试，并覆盖计划 IPC 控制消息 |
| 重试、回退、预取落盘和读取，最终进度快照丢失 | 网络量等于各请求尝试实际接收量；临时文件读取不重复计数；文件数不随切片增加 | 复用网络汇总与最终结果补齐测试 |

必要的传输校验必须覆盖错误 `Content-Range`、短响应和不同版本数据最终哈希不匹配，不能仅测试理想的范围服务。IPC 增加的范围解析请求必须验证计划结束后能完成或终止等待，不能留下永久 pending。

### 单次验收和参数比较

使用现有 DFS2 e2e 入口增加一个聚合场景，覆盖任意 range 申报、跨节点切片、一次片级重试及整文件回退；选择一次真实提权执行验证控制消息往返和暂存权限。不新增 CI job 或按数据源展开矩阵。范围算法与调度排列由单测保护，UI 文案、具体组数和瞬时速度不固定为永久快照。

一次验收比较多小文件更新、一个压缩后超过 100MiB 的文件、多个大文件混合小文件三类输入。对照当前实现，记录总完成时间、收尾耗时、请求数、实际字节、内存、临时磁盘峰值和同配置 release 二进制体积。补充一组极小补丁与连续全量文件，以及快、慢磁盘上的预取比较；性能比较作为调参记录，不设置易受环境影响的 CI 耗时阈值。

25MiB 及其他初始参数通过这些输入调整。服务端示例值与本地默认值分别验收，确认较低并发、大切片能减少请求，较多可用节点时能利用文件间和片间并行；不承诺服务器负载与最优参数之间存在固定单调关系。

复用现有 builder 确定性夹具验证排序与数据内容不变，并以旧版读取同一代表性包确认格式兼容。该项是本次变更验收，不为每个 hint 值重复构建包。现有基于格式边界的必要单测继续保留。

### Python 原型与规划测量

[脚本原型](../../../scripts/planner_lab/planner.py)实现在线应用数据的当前策略复现、全量与补丁局部比较、范围合并、尾组调整和均分切片；[包读取器](../../../scripts/planner_lab/package_reader.py)只读扫描 TLV，并逐项核对索引与物理偏移。[基准入口](../../../scripts/planner_lab/bench.py)区分真实包完整内容、真实版本清单差分和固定种子的合成选择集合。原型不含安装器自身映像生成、用户目录扫描、离线混合基文件、运行库、HTTP 执行和提权。

### 25MiB 上限下的参数与调度参考

本节记录规划阶段的参考值，不将模型时间固定为回归阈值。[参数扫描脚本](../../../scripts/planner_lab/sweep.py)、[汇总脚本](../../../scripts/planner_lab/summarize_sweep.py)和已有测试保留，供正式接入时对照。25MiB 为此次模拟 CDN 范围大小约束的测试值，等于 26,214,400 字节，不修改生产默认上限；实际服务端建议按字节传递，不能把 CDN 的十进制 MB 阈值直接当作 MiB。模型没有模拟缓存命中率。

输入共 12 组：上述三个真实完整内容或更新集合；以种子 17、71、173 从 BetterGI 完整清单独立抽取约 20% 文件的三个稀疏更新集合；一万个小文件加 100MiB、110MiB、225MiB 大文件；单个 110MiB；五个 110MiB；100MiB、110MiB、225MiB、350MiB、40MiB、25.001MiB 混合；25MiB、50MiB 及两侧各 0.001MiB 的边界集合；一千个小文件加三个原始体积顺序与压缩体积顺序相反的大文件。合成文件只生成索引与大小，不分配对应内容。

每文件在途限制会改变参数结论。没有该限制时，真实更新在等速四节点上使用 15MiB 加借用得到 3.977 秒，限制为 3 后变为 5.408 秒。单个 110MiB 文件在单请求限速模型中，25MiB 目标形成五个 22MiB 请求，上限 3 时为 5.660 秒，上限 5 时为 2.830 秒；但后四片完整预取需要 88MiB 暂存，多个文件不能各自无限扩大窗口。这些上限只约束在途请求，尚未计入已下载但未被解码器消费的数据，不能据此证明 256MiB 全局磁盘预算足够。

在生产包原布局上，只把客户端合并资格从 1MiB 提高到 2MiB，使三个真实输入的请求数从 69、57、18 降至 64、55、17，传输分别增加 210、84、42 字节。该实验没有调整生成器分类，只反映现有布局中的相邻文件合并。例如 BetterGI 更新额外合并的两个文件原始体积约为 1.603MiB 和 1.024MiB，它们在现有大文件区域已相邻，中间只有 42 字节 TLV 头部；这个收益不能代表按更新状态重排后的效果。

15MiB 合并目标在部分模型中更快，也会改变节点分配及收尾；目前保留 10MiB。额外字节限制降为 0% 会阻止跨越 TLV 间隔，12 个输入的总请求数达到 20% 方案的 16.09 倍，暂不收紧现有比例。按压缩体积排序或按剩余字节选择额外切片均未稳定优于现有顺序，暂不引入更复杂的排序成本模型。

25MiB 上限、25MiB 和 15MiB 目标分别对三个真实输入执行压缩字节回放，全部 SHA-256 校验通过。两种目标分别核对 1730、85、123 个参与合并或切片的数据项。25MiB 目标的后续片临时写入量为 66,499,907、31,494,763、50,015,613 字节；15MiB 目标为 72,751,859、31,494,763、56,267,565 字节。这是累计写入量，不是磁盘峰值；较小首片让更多字节经过临时文件。回放未验证解码速度、HTTP 失败或预取背压。

当前保留 25MiB 切片目标，将借用空闲名额作为优先进入受控传输验证的调度候选；10MiB、15MiB 保留为服务器建议和后续调参的比较值。需要同时验证网络、顺序解码、已完成片的驻留时间及磁盘预算，再决定每文件窗口是否从固定片数改为按可用字节放宽。该决定先于 Rust 接入，不据事件模型直接放宽生产资源限制。

### 生成器与客户端同时采用 2MiB 的参考

[布局模拟脚本](../../../scripts/planner_lab/layout_sweep.py)按生成器的大文件、未变化小文件、变化或新增小文件、小补丁、大补丁五类及名称排序，只重新计算索引偏移。应用文件按原始体积分组，补丁按 metadata 中未压缩补丁的大小分组；保留现有压缩长度、共享 payload 去重、TLV 头部、补丁集合和固定前缀。将分类阈值从 1MiB 改为 2MiB，不改变生成补丁时跳过小于 1MiB 文件的既有规则，也不重新生成或压缩内容。完整安装的规划输入与生成包时采用的更新基准分别传入，避免把完整安装误当作首次生成包。

以 BetterGI 0.64.0 作为生成 0.65.0 的唯一旧版本基准时，模拟的 1MiB 分类精确复现原包 1779 个数据项的全部偏移。对共享内容使用与生成器相同的按 hash 判断变化规则；[布局单测](../../../scripts/planner_lab/test_layout.py)覆盖应用文件与补丁的分类依据、同一内容对应多个路径和重复重排的稳定性。布局模拟加原有规划测试共 11 项通过。

KongYingMap 缺少旧版本，因此两个虚拟布局均假定全部文件为新增；1MiB 虚拟布局有 78 个数据项偏移与生产包不同，只能作为该假设下的完整安装比较。另用三个种子在 BetterGI 真实清单上构造约 20% 变化的旧版本，及三个含 1000 个文件的合成版本对：70% 文件从 1KiB～1MiB 取样，25% 从大于 1MiB～2MiB 取样，5% 从大于 2MiB～5MiB 取样，压缩长度为原始长度的 20%～90%；更新文件独立抽取约 20%。这些构造更新没有生成补丁。每组均比较原布局、1MiB 虚拟布局和 2MiB 虚拟布局，以及两种客户端资格上限。

## Risks

切片落盘增加压缩字节的磁盘写入和读取，在机械硬盘或磁盘已饱和的设备上可能抵消网络并行收益。预取窗口、磁盘预算和第一片直供需要联合测量；资源不足时应减少预取或使用单流，不通过扩大内存绕过预算。

顺序解码仍可能被靠前的慢切片阻塞。规划器优先调度所需范围并允许重试，但不引入重复竞速请求；如果网络已经足够快而解码受限，增加切片不会继续提速。

固定落盘、范围解析往返、文件间调度及错误状态会增加代码与二进制体积。实现优先复用 Tokio、现有 HTTP 客户端、临时目录和压缩库，不新增通用调度框架或下载依赖。合并算法按有限候选计算，避免规划成本在多小文件场景接近平方增长。

小文件取舍仍偏向减少请求，不能保证每个网络环境下最短耗时。服务端建议也可能在一次安装中变得过时；这些影响属于性能退化，不应改变文件内容、提交安全性或成功判定。

私有 IPC 从独立文件操作扩展到统一计划执行，改动范围较大，必须与取消和网络计数设计共同检查。先单独验证纯规划函数，再接入执行器、提权与前端统计；本提案不要求同时重写安装提交、运行库或宿主界面。
