# 网络下载速度与离线安装展示

Status: proposed

## Problem

[安装过程信息展示对齐](./2026-09-21-progress-information-parity.md)定义了活动文件、完成量和数据处理速度。数据处理可能来自本地解压、补丁输入或下载后的写入，无法单独说明网络接收速度。直接将处理速度替换为网络速度，又会使纯离线安装失去速度信息。

[NetworkInsightStream](../../../native/fs.rs)在安装包解压之前统计响应体字节，普通下载与合并下载都经过它。[Mirror酱 下载](../../../native/thirdparty/mirrorc.rs)和[在线运行库](../../../native/installer/runtimes.rs)也使用同一下载入口。现有原子计数为 `u64`，用于诊断的 `InsightItem.size` 为 `u32`，且通过 `try_lock` 更新；实时速率应直接读取原子计数。

[安装数据源](../../../native/session/run.rs)按文件选择本地或 URL，[混合补丁](../../../native/ipc/install_file.rs)可以先解压本地基文件再读取在线补丁。安装包是否包含离线资源，不能决定整个会话的速度含义。提权执行时，[进度通道](../../../native/ipc/manager.rs)允许丢弃积压消息，操作结果也可能先于最后一条进度被处理。

## Proposal

### 网络速度的计量范围

统计安装文件、补丁、Mirror酱 归档和在线运行库的下载响应体字节，在安装包解压之前计数。重试和 fallback 已接收的字节继续累计，合并下载按请求计数一次，包括为到达后续文件而读取并跳过的数据。纯本地读取不进入网络计数。

chunk 本身已经经过 zstd 压缩，下载服务预期直接提供资源字节，不通过 HTTP `Content-Encoding` 二次压缩。沿用现有下载客户端与解码行为，以客户端交付的响应体作为计量位置。若服务器额外启用 HTTP 内容编码，自动解码可能使这个计数大于压缩后的传输量；这一限制保留在统计口径中，不为速率展示另建解码流程。API 小请求、协议开销和外部运行库安装进程自行产生的流量不在统计范围内。

### 进度字段与显示选择

完整 Rust、TypeScript 结构及 JSON 示例统一放在[进度接口提案](./2026-09-21-progress-information-parity.md)。保留 `processing_bps`，新增 `network_bps: Option<u64>` 和 `network_pending: bool`；TypeScript 分别使用 `number | null` 和 `boolean`。两个速率字段的单位均为 B/s，含义固定。

`network_pending` 由会话按当前执行计划和任务状态生成。当前下载阶段仍有需要接收的数据时为 `true`，包括排队、连接、接收和等待重试。下载工作全部结束或被放弃后为 `false`，剩余的解压、校验、刷盘不延长它。fallback 新增在线任务时重新置为 `true`。本地任务和嵌入运行库不会单独使它变为 `true`。

`network_bps` 为 `null` 表示采样不足或当前没有网络工作；有完整采样但没有接收数据时为 `0`。`network_pending: false` 时同时将 `network_bps` 清为 `null`。前端通过 `network_pending` 选择速度含义，不能通过速率是否大于零判断是否仍在下载。

| 实际工作 | 速度展示 | 其他进度信息 |
|---|---|---|
| 纯离线解压或补丁处理 | 展示 `processing_bps`，与当前处理动作关联 | 保留完成量、活动文件及逐文件进度 |
| 在线下载或本地与在线并行 | 展示 `network_bps`，与下载动作关联 | 活动列表继续展示各文件实际动作和进度 |
| 下载等待、停顿或重试 | 采样充分时显示网络零速率；采样不足时暂不显示数值 | 保留下载或重试状态，本地任务继续显示自己的进度 |
| 下载完成，只剩本地处理 | 切换为 `processing_bps`，同时更新对应动作 | 保留剩余文件及其处理进度 |
| 校验、刷盘或提交 | 没有适用的速度时省略数值 | 展示当前动作和已有计数 |

总体区域同时只展示一种速度，速度数值与对应动作放在一起。完成量与总量继续采用[处理计数规则](./2026-09-21-progress-information-parity.md)，不随速度切换。网络接收量与解压输出量不能相加，也不能用网络速率推算安装百分比。native 和 WebView 使用相同的选择规则。

嵌入运行库提取期间展示本地处理信息，启动其安装程序后展示运行库安装状态。在线运行库也在接收结束后清除网络速度，安装程序的运行时间不计入下载等待。

### 计数传递与采样

复用下载流中的 `u64` 原子计数，在执行侧按 IPC 操作汇总累计接收量，并传递网络读取开始和结束状态。单文件、合并下载、Mirror酱 和运行库共用计数方式，逐文件处理事件继续用于活动列表。

进度事件携带本次操作的累计字节数。会话通过现有 IPC 操作标识关联计数，保存已收到的最大值，只累计增加部分；重试产生的新操作单独累计。这样，中间快照丢失或较旧的快照晚到都不会重复计数或产生负速率。

操作返回时，最终累计量随现有成功或失败结果带回，会话补齐尚未计入的部分后结束该操作的统计，忽略其迟到进度。最终计数使用同一原子值，不使用文件目标大小或诊断摘要替代。会话取消后按现有取消与清理流程结束统计，不为等待速率消息延长取消。

新增速率统计在字节读取时只更新计数，网络进度快照最多每约 100 ms 发布一次；读取结束补发最终快照。会话复用[现有提案中的定时采样规则](./2026-09-21-progress-information-parity.md)，按全部操作累计接收量的差值计算每秒速度。定时器独立于读取回调，停顿时仍能产生零速率；退出运行状态后停止更新。

### 与进度展示和取消处理的关系

网络统计复用 UI 信息量功能的会话汇总器、状态快照和速率采样，不建立独立的前端计时器或第二套进度状态。下载与本地处理并行时，活动列表负责保留每个任务的信息，速率选择由会话状态决定。

取消受理、提交和清理顺序遵守[重构审阅问题与修复建议](./2026-09-20-refactor-review-fixes.md)。取消提示优先于速度刷新；增加网络统计不能改变用户取消、连带中止和真实失败的分类。两个功能需要共同验证这些共享行为。

## Alternatives considered

- 将处理速度全部替换为网络速度：纯离线安装没有网络字节，解压和补丁工作会失去速度信息。
- 在同一个速率字段中交替填入网络和处理数值：消费者无法确认数值含义，下载停顿也容易被误判为应切换到本地处理。保留独立字段及明确的下载状态。
- 常驻显示两种速度并增加逐文件网速：增加界面占用和合并请求的分摊逻辑。总体速度配合活动文件进度即可表达当前工作。
- 在前端对完成量求差：解压、补丁、重试重置和结束补齐都可能改变完成量，不能还原网络接收量。
- 为速率引入更底层流量监控或独立 HTTP 解码：会扩大实现和依赖范围。采用正常资源交付条件下的响应体计数，并记录额外 HTTP 内容编码的限制。

## Acceptance criteria

### 需要保留的回归测试

关键测试集中在计量位置、累计规则和下载状态，复用现有进度、IPC 与组件测试。采样算术及通用快照生命周期共用[UI 信息量提案的回归测试](./2026-09-21-progress-information-parity.md)，不另写一套相同测试。

| 要测试的场景 | 必须核对的结果 | 验证方式 |
|---|---|---|
| 网络 zstd chunk 解压；同样的数据从本地读取；合并响应内读取多个 chunk 及跳过间隔 | 网络量等于实际读取的压缩响应体字节，不等于解压输出；本地读取网络量为零；合并请求包含跳过的字节且只累计一次 | 一个小型内存压缩夹具，经过实际计数包装与解码路径，覆盖普通 AsyncRead 和合并 Stream 两种入口 |
| 多个操作交错上报；同一操作快照丢失、重复或乱序；累计值跨过 `u32` 范围 | 各操作只累计新增部分，较旧值不使总量回退，重复值不重复增加，使用 `u64` 保持完整计数 | 用少量累计值构造汇总单测，无需分配大文件或传输同等大小数据 |
| 请求失败后重试，合并失败后 fallback 为多个单文件请求 | 失败尝试已接收的字节保留，新操作独立累计，合并请求与 fallback 各自的实际流量只计算一次 | 在同一汇总夹具中模拟操作开始、失败和后续累计事件，检查最终总量 |
| 成功或失败结果先于最后进度到达；结果后又收到进度 | 返回结果中的最终计数补齐未收到的字节，后续消息不重复计数或恢复已结束的操作 | 扩展现有 IPC 测试，用通知信号控制到达顺序；仅验证汇总函数不足以证明结果传递正确 |
| 排队、连接、接收停顿、等待重试；读取结束但文件仍在校验或刷盘；fallback 新增下载 | 前四种状态保持 `network_pending`；全部下载读取结束后变为 `false` 并清空网速，校验和刷盘不延长网络等待；新增在线工作后恢复为 `true` | 会话状态序列测试，使用可控读取结束与文件操作结束信号，核对二者的区别 |
| 纯离线处理；嵌入运行库提取；在线与本地并行；网络为零或样本不足但本地速度非零；下载完成后继续本地处理 | 离线显示处理速度；有下载工作时选择网络速度，零值和 `null` 都不会误切为处理速度；下载结束后切换含义且完成量不变；运行库安装程序启动后不残留下载速度 | 一组共享快照及组件输入变体，验证会话字段和界面选择结果，不固定标签文字 |

停顿归零必须覆盖“没有任何新字节回调，只有采样时钟推进”的情况。会话退出后的晚到消息、取消提示优先级继续复用[UI 信息量验收](./2026-09-21-progress-information-parity.md)和[取消修复验收](./2026-09-20-refactor-review-fixes.md)，网络进度作为其中一种晚到事件输入。

### 一次性验收

以下检查确认各入口接线和实际展示，不为每种下载来源或安装模式新增长期 e2e 场景。

| 要检查的场景 | 验收结果 |
|---|---|
| 单文件、合并请求、Mirror酱 和在线运行库入口 | 核对各入口都接入同一网络统计设施，开始、读取结束及操作返回能传到会话；嵌入资源没有误用在线计数 |
| 代表性的在线、纯离线及混合安装 | 在已有安装验收中观察速度与动作的对应关系、网络停顿和下载结束后的切换；活动文件与处理计数持续可见，不以是否携带离线资源决定整个会话的语义 |
| 提权执行与普通执行 | 选用相同的小型下载数据，确认网络字段能经过真实提权通道到达会话；累计结果符合夹具大小，不要求两个执行环境的瞬时速率相等 |
| 连续下载、多个任务完成和退出运行状态 | 观察网络快照受到限频，读取没有每次都发送 IPC 消息；完成操作释放明细，仅保留汇总值，结束后无持续采样任务 |

两个渲染器的展示一致性、前端与安装器体积、进度更新开销统一采用[UI 信息量的一次性验收](./2026-09-21-progress-information-parity.md)。记录构建条件与观察结果，不增加固定网速、CPU 占用、精确调度间隔或二进制字节数的长期阈值。额外 HTTP 内容编码仍按已声明的统计限制处理，不为未支持的严格流量计量增加测试矩阵。

### 验证记录

实施时记录关键回归用例、执行结果和一次性验收的环境；未覆盖入口或未执行场景明确列出。真实下载观察用于确认接线和交互，计数正确性由上述可控输入测试证明，二者分别记录。

## Risks

响应体按消费者读取节奏交付，解压或磁盘写入的背压可能使速率呈现短时波动；提权消息延迟也会影响采样分布。每秒采样适合展示下载进展，不能据此推断链路的最大带宽。

正常资源交付不使用额外 HTTP 内容编码是这里的计量前提。若服务端改变这一行为，需重新核对响应体计数的含义。

`network_pending` 若仅跟随字节回调，会在停顿时错误切换速度；若跟随整个文件操作结束，又会把校验和刷盘算成下载等待。实现需结合下载计划与响应体读取生命周期更新。

两项功能都会修改会话进度、提权事件和渲染器。接口、采样和取消状态应共用实现，避免分别维护任务完成判断与速率计时。
