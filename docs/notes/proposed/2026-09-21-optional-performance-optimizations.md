# 安装与打包的可选性能优化

Status: proposed

## Problem

安装器需要兼顾运行性能、二进制体积和维护成本。[编译配置级体积裁剪](../implemented/2026-09-02-profile-size-trim.md)采用全局体积优化、哈希依赖单独 O3；[文件提交协议](../implemented/2026-09-02-atomic-file-commit.md)采用目录枚举和整目录提交；[提权管道帧编码](../implemented/2026-09-02-ipc-postcard-frames.md)减少了私有 IPC 的编码成本。这些已有取舍应保留，新的优化需要证明额外收益。

代码分析仍发现若干重复工作。以下成本来自 `a52a4c66a9e75d86c130be2e029345a761829c24` 的实现，尚未通过基准测量确认其耗时占比；它们是可独立选择的候选，不构成必须全部实施的任务清单。嵌入包扫描、本地哈希调度与写入后重读校验三项的实现与测量见[共享包读取与边写边校验的写出管线](../implemented/2026-11-04-pack-reader-and-write-pipeline.md)，不在本提案范围内。

| 路径 | 当前成本 | 主要受影响场景 |
|---|---|---|
| [安装计划](../../../native/session/plan.rs)与[提交计划、下载操作构造](../../../native/session/run.rs) | 每个文件线性查找本地记录、metadata 和补丁；部分查找反复规范化路径并分配字符串。每个候选目录又遍历文件清单。 | 多文件更新，部分计算随文件数接近平方增长。 |
| [builder 打包](../../../native/builder/pack.rs) | 排序键计算反复搜索分类并创建名称字符串；收集条目时线性查重。 | 文件和补丁较多的打包任务。 |
| [Mirror酱 解压](../../../native/thirdparty/mirrorc.rs) | 每个文件分配一块 256 KiB 缓冲区。 | 归档内文件很多的 Mirror酱 更新。 |
| [下载进度汇总](../../../native/session/run.rs) | 每次刷新遍历所有文件，重新计算总量、完成量和活动文件。 | 待处理文件很多、下载持续时间较长的会话。 |

## Proposal

### 一次建立计划查询索引

在本次计划计算期间建立规范化路径到本地记录、目标文件 metadata、嵌入名称和补丁候选的查询索引，保存引用或数组位置，避免复制整份记录。路径只规范化一次，继续使用现有比较规则；文件展示名和打包名保留原样。

目录整体提交的候选条件改为遍历文件时向父目录累计，复用现有容器，不引入通用路径树。目录是否干净、是否包含 reparse point、是否所有受管文件都将被替换，仍采用既有判据；提交前的重新检查保留。

补丁候选、重复名称和输出顺序必须保持原来的选择结果，不能因改用 `HashMap` 而变成任意取一个。索引只活到本次会话所需阶段，不持久化，不建立全局缓存。此项以少量临时内存换取查找与字符串处理的减少，主要针对多文件场景。

### 复用 Mirror酱 解压缓冲区

[Mirror酱 解压](../../../native/thirdparty/mirrorc.rs)的 256 KiB 缓冲区可移到文件循环外复用，属于局部优化，不改变解压、摘要与刷盘语义。

### 简化 builder 排序与查重

预先建立名称到打包优先级的映射，用集合判断已经收录的内容；排序直接比较优先级和已有名称，避免在比较期间搜索分类、构造字符串。名称出现在多个分类时保留当前优先级选择，相同优先级保持原有名称排序，最终条目顺序与编码不变。

此项改善打包耗时，不计作用户安装速度收益。实现尽量留在 builder 使用的代码中，不把仅供打包的辅助结构引入安装器运行路径。

### 根据测量决定是否增量汇总进度

进度汇总可以缓存总量，并按每个文件的变化更新完成量。字段含义和重试处理以[过程信息展示对齐](./2026-09-21-progress-information-parity.md)为准；不能把成功时补齐的虚拟进度计入速度。只有汇总成本值得处理时才实施增量计算，不为低频、小文件集维护额外计数状态。

## Alternatives considered

- 全局改为 O3 或扩大内联：已有体积测量支持当前配置。优先减少算法重复工作；仅当局部 CPU 热点有证据时重新评估编译覆盖。
- 直接提高下载、哈希或解压并发：可能增加内存、磁盘争用和调度成本，不能保证吞吐提升。本提案不增加并发配置项或复杂流水线。
- 按大小、修改时间缓存哈希并跨会话复用：会改变扫描的正确性前提，且已有[文件提交协议](../implemented/2026-09-02-atomic-file-commit.md)明确不采用。会话内的查询索引不承担判断文件内容是否变化的职责。
- 去掉逐文件刷盘：降低了持久性保证，不属于等价性能优化。
- 一次性重写所有热点并增加完整性能测试体系：难以归因，也容易使测量设施的维护成本超过优化收益。逐项比较，只保留收益足以解释体积和复杂度代价的改动。

## Acceptance criteria

每个候选独立决定是否实施。没有收益或收益不足的候选可以放弃，不以实现数量作为完成标准。

| 候选 | 行为约束 | 最小比较范围 |
|---|---|---|
| 计划索引 | 安装、跳过、补丁选择和提交单元与现有规则一致。 | 一个多文件清单，单独记录计划生成耗时及峰值内存；复用现有计划测试保护语义。 |
| Mirror酱 解压缓冲区复用 | 解压产物、md5 与删除清单不变。 | 复用现有 Mirror酱 解压单测，不单独比较耗时。 |
| builder 排序与去重 | 相同输入的条目顺序和包编码不变。 | 一个包含打包分类和重复内容的输入，比较处理耗时，复用小型确定性样例校验结果。 |
| 增量进度 | 显示口径先明确，收益独立可见。 | 只在测量表明这一处占比值得优化时增加对应比较。 |

性能数据使用独立基准或短脚本收集，不进入带耗时阈值的单测，不新增 CI job 或 e2e 矩阵。每项比较同时记录输入规模、工具链、target、release profile、磁盘和缓存条件、测量工具及耗时波动；工具配置相同的前后结果才可比较。普通文件重复运行属于热缓存，不标记为冷启动。

体积同时比较同一构建配置下 installer 和 builder 的 exe 字节数；出现增量时按需要检查 PE 节或符号，避免仅凭依赖树推测。查询索引还需记录峰值内存。对于收益接近测量波动、却增加体积或维护逻辑的改动，默认不采用。

只为确定性打包结果与计划选择结果等关键行为补必要单测；已有计划用例能够保护的规则直接复用。提案编写不运行构建、基准、CI 或 e2e。

## Risks

查询索引会占用额外临时内存，路径规范化和重复项处理不当还可能改变计划结果。优先选择复用数据，避免建立多个表示同一事实的长期状态。

不同磁盘、文件数量和缓存状态可能得到不同的主要耗时。上述优先级是代码分析结论，不是实测收益排名。实现时保留独立比较结果和未覆盖的场景，不将局部加速外推为整体安装加速。
