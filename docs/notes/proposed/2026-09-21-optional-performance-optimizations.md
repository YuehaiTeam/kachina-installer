# 安装与打包的可选性能优化

Status: proposed

## Problem

安装器需要兼顾运行性能、二进制体积和维护成本。[编译配置级体积裁剪](../implemented/2026-09-02-profile-size-trim.md)采用全局体积优化、哈希依赖单独 O3；[文件提交协议](../implemented/2026-09-02-atomic-file-commit.md)采用目录枚举和整目录提交；[提权管道帧编码](../implemented/2026-09-02-ipc-postcard-frames.md)减少了私有 IPC 的编码成本。这些已有取舍应保留，新的优化需要证明额外收益。

代码分析仍发现若干重复工作。以下成本来自 `a52a4c66a9e75d86c130be2e029345a761829c24` 的实现，尚未通过基准测量确认其耗时占比；它们是可独立选择的候选，不构成必须全部实施的任务清单。

| 路径 | 当前成本 | 主要受影响场景 |
|---|---|---|
| [嵌入包扫描](../../../native/local.rs) | `search_pattern` 遍历整个 exe 收集魔数位置，随后才解析条目并排除载荷内部的命中。`OnceCell` 仅避免同一进程重复扫描。 | 大离线包首次启动，需要读取和检查并不参与配置解析的载荷。 |
| [安装计划](../../../native/session/plan.rs)与[提交计划、下载操作构造](../../../native/session/run.rs) | 每个文件线性查找本地记录、metadata 和补丁；部分查找反复规范化路径并分配字符串。每个候选目录又遍历文件清单。 | 多文件更新，部分计算随文件数接近平方增长。 |
| [哈希实现](../../../native/utils/hash.rs)与[扫描调度](../../../native/fs.rs) | 每文件分配 1 MiB 缓冲区；先为所有文件创建异步任务，再由信号量限制哈希，每次哈希另行进入 `spawn_blocking`。 | 大量小文件，调度和分配可能占据较高比例。 |
| [builder 打包](../../../native/builder/pack.rs) | 排序键计算反复搜索分类并创建名称字符串；收集条目时线性查重。 | 文件和补丁较多的打包任务。 |
| [文件写入收尾](../../../native/ipc/install_file.rs) | 写入后重新打开并读取目标文件计算哈希，刷盘另开句柄。 | 大文件、本地解压或磁盘受限场景；操作系统缓存可能降低实际磁盘读取成本。 |
| [下载进度汇总](../../../native/session/run.rs) | 每次刷新遍历所有文件，重新计算总量、完成量和活动文件。 | 待处理文件很多、下载持续时间较长的会话。 |

## Proposal

### 优先验证离线包扫描

将寻找条目和解析条目合并：定位并验证条目头后，利用已有 TLV 长度跳过内容区，继续读取后续条目，不先扫描全部载荷。已有包索引可辅助定位，但不能只使用索引而漏掉 `append` 添加的未索引条目。无法直接定位的区域保留必要的搜索路径。

复用现有 mmap 和解析设施，不为魔数搜索引入新依赖。生产格式的魔数、字段宽度、字节序及排列不变；已有包、追加运行库、清除索引标记后的映像仍可读取。名称与长度校验由[重构审阅问题与修复建议](./2026-09-20-refactor-review-fixes.md)定义，性能优化不另立更宽松的读取规则。

预期收益是少读取载荷、少执行逐字节比较、减少无效魔数位置的存储。体积代价应限制在定位和遍历逻辑；先比较大离线包的首次解析耗时，同时确认小在线安装器没有明显退步。

### 一次建立计划查询索引

在本次计划计算期间建立规范化路径到本地记录、目标文件 metadata、嵌入名称和补丁候选的查询索引，保存引用或数组位置，避免复制整份记录。路径只规范化一次，继续使用现有比较规则；文件展示名和打包名保留原样。

目录整体提交的候选条件改为遍历文件时向父目录累计，复用现有容器，不引入通用路径树。目录是否干净、是否包含 reparse point、是否所有受管文件都将被替换，仍采用既有判据；提交前的重新检查保留。

补丁候选、重复名称和输出顺序必须保持原来的选择结果，不能因改用 `HashMap` 而变成任意取一个。索引只活到本次会话所需阶段，不持久化，不建立全局缓存。此项以少量临时内存换取查找与字符串处理的减少，主要针对多文件场景。

### 复用哈希缓冲区并限制待执行任务

由数量有限的哈希工作任务连续处理文件，每个任务复用自己的缓冲区，避免为每个文件同时创建一个等待信号量的任务，再单独调度阻塞哈希。复用现有 Tokio 运行时和阻塞任务设施，不增加线程池依赖。保留顺序读取、结果错误传播和进度更新语义。

并发数通过代表性目录比较后选择简单上限，不直接假定逻辑 CPU 越多、磁盘越快，也不新增磁盘型号识别或自适应调参系统。取消应在文件或读取边界响应，但是否接受取消及何时清理仍遵守[取消修复提案](./2026-09-20-refactor-review-fixes.md)。

[Mirror酱 解压](../../../native/thirdparty/mirrorc.rs)的 256 KiB 缓冲区可移到文件循环外复用，属于同类局部优化，无需与哈希调度重写绑定实施。

### 简化 builder 排序与查重

预先建立名称到打包优先级的映射，用集合判断已经收录的内容；排序直接比较优先级和已有名称，避免在比较期间搜索分类、构造字符串。名称出现在多个分类时保留当前优先级选择，相同优先级保持原有名称排序，最终条目顺序与编码不变。

此项改善打包耗时，不计作用户安装速度收益。实现尽量留在 builder 使用的代码中，不把仅供打包的辅助结构引入安装器运行路径。

### 根据测量决定是否减少重复读取和进度遍历

写入时计算哈希仅作为后续候选。普通顺序写入可能复用正在处理的数据，补丁输出、安装器索引标记修改等路径仍需验证最终内容。将“重新读取最终文件校验”改成“校验写入流”会改变能够发现的问题范围，必须先确认校验要求，再决定哪些路径可合并。保留每个产出文件的刷盘及 journal 持久化要求，不用删除 `sync_all` 换取性能数字。

进度汇总可以缓存总量，并按每个文件的变化更新完成量。字段含义和重试处理以[过程信息展示对齐](./2026-09-21-progress-information-parity.md)为准；不能把成功时补齐的虚拟进度计入速度。只有汇总成本值得处理时才实施增量计算，不为低频、小文件集维护额外计数状态。

## Alternatives considered

- 全局改为 O3 或扩大内联：已有体积测量支持当前配置。优先减少算法重复工作；仅当局部 CPU 热点有证据时重新评估编译覆盖。
- 直接提高下载、哈希或解压并发：可能增加内存、磁盘争用和调度成本，不能保证吞吐提升。本提案不增加并发配置项或复杂流水线。
- 仅用包索引替代全部扫描：遗漏未索引追加条目，也不能覆盖索引标记被清除的映像。利用条目长度跳过载荷，仍需保留兼容定位方式。
- 按大小、修改时间缓存哈希并跨会话复用：会改变扫描的正确性前提，且已有[文件提交协议](../implemented/2026-09-02-atomic-file-commit.md)明确不采用。会话内的查询索引不承担判断文件内容是否变化的职责。
- 去掉写后校验或逐文件刷盘：降低了完整性或持久性保证，不属于等价性能优化。
- 一次性重写所有热点并增加完整性能测试体系：难以归因，也容易使测量设施的维护成本超过优化收益。逐项比较，只保留收益足以解释体积和复杂度代价的改动。

## Acceptance criteria

每个候选独立决定是否实施。没有收益或收益不足的候选可以放弃，不以实现数量作为完成标准。

| 候选 | 行为约束 | 最小比较范围 |
|---|---|---|
| 包扫描 | 新旧有效包得到相同条目、配置和偏移；追加条目可发现；既有越界与截断检查保留。 | 一个代表性大离线包和一个小在线安装器，比较首次解析耗时与读取量；缓存状态相同的运行互相比。 |
| 计划索引 | 安装、跳过、补丁选择和提交单元与现有规则一致。 | 一个多文件清单，单独记录计划生成耗时及峰值内存；复用现有计划测试保护语义。 |
| 哈希与缓冲区复用 | 哈希、错误和扫描结果不变；在途数量有界；取消后的清理顺序不变。 | 一个多小文件目录及一个大文件，比较扫描耗时、内存与并发设置。 |
| builder 排序与去重 | 相同输入的条目顺序和包编码不变。 | 一个包含打包分类和重复内容的输入，比较处理耗时，复用小型确定性样例校验结果。 |
| 写入流校验、增量进度 | 校验语义与显示口径先明确，收益独立可见。 | 只在前面的测量表明这两处占比值得优化时增加对应比较。 |

性能数据使用独立基准或短脚本收集，不进入带耗时阈值的单测，不新增 CI job 或 e2e 矩阵。每项比较同时记录输入规模、工具链、target、release profile、磁盘和缓存条件、测量工具及耗时波动；工具配置相同的前后结果才可比较。普通文件重复运行属于热缓存，不标记为冷启动。

体积同时比较同一构建配置下 installer 和 builder 的 exe 字节数；出现增量时按需要检查 PE 节或符号，避免仅凭依赖树推测。哈希索引和工作任务还需记录峰值内存。对于收益接近测量波动、却增加体积或维护逻辑的改动，默认不采用。

只为包解析边界、确定性打包结果以及调度改变影响的关键行为补必要单测；已有计划和哈希用例能够保护的规则直接复用。提案编写不运行构建、基准、CI 或 e2e。

## Risks

包扫描优化可能遗漏追加条目，或把映像内部的伪魔数当作起点；直接跳过载荷必须建立在有效条目解析之上。它减少的是应用自身的读取，不能保证消除操作系统或安全软件对整个 exe 的扫描。

查询索引会占用额外临时内存，路径规范化和重复项处理不当还可能改变计划结果。工作任务减少调度开销，但批次分配不均或并发上限不合适也可能拖慢大文件扫描。优先选择复用数据和有界调度，避免建立多个表示同一事实的长期状态。

不同磁盘、文件数量和缓存状态可能得到不同的主要耗时。上述优先级是代码分析结论，不是实测收益排名。实现时保留独立比较结果和未覆盖的场景，不将局部加速外推为整体安装加速。
