# 下载规划器：范围合并、切片与文件间调度

Status: implemented

## Problem

[下载合并](../../../native/session/merge.rs)通过增加少量传输字节减少请求数量；小文件使用合并全量请求，即使存在补丁，也可能比独立请求补丁更快。这是需要保留的性能取舍。文件获取同时受请求数量、节点分布、压缩数据量、解码开销和磁盘速度影响，不能只按补丁大小选择方案。

规划器接入前，执行器按大任务 5、小任务 11、本地任务 16 限制并发，单个大文件对应一个下载流，其他任务完成后它可能成为最后一个长时间运行的任务。直接在每个文件内部增加并发，又会使实际请求数乘以切片数量，并让少数大文件占满下载名额。

[builder 分类](../../../native/builder/gen.rs)按原文件大小 1MiB 区分大、小文件，将未变化的小文件、变化或新增的小文件、小补丁和大补丁分别归类。[打包排序](../../../native/builder/pack.rs)按分类顺序和内容名称排列，形成较连续的更新数据区域。规划器接入前，客户端按 500KiB 接纳小文件、按包内偏移贪心合并，最大合并范围 10MiB、额外字节比例不超过 20%。包内 metadata 清除了 `packing_info`，规划只能利用实际索引位置，分类信息不随包传递。

DFS 调度器接受资源内部的任意合法 range。服务端可以建议切片大小和并发，客户端需要将这些建议用于统一规划，并处理切片乱序、临时落盘、范围重试和整文件回退。服务端建议描述运行时调度，不改变生产包格式。

## Decision

规划器负责应用文件及补丁的范围合并和切片，执行器负责请求调度、按顺序供给解码器、校验与收尾。提交沿用[文件提交协议](./2026-09-02-atomic-file-commit.md)。规划只读索引偏移，不向包 metadata 添加字段，不改变 builder 的分类、条目顺序、压缩数据与索引编码；切片只划分已有压缩字节，不重新压缩、不插入分帧信息。运行库与 Mirror酱 归档不经过规划器，只共用网络统计；Mirror酱 归档的下载单独开一个并发为 1、预取预算为 0 的下载会话。

### 服务端建议与本地策略

DFS2 metadata 请求（[`get_dfs2_metadata`](../../../native/dfs.rs)）在读取响应体之前解析四个十进制响应头，结果作为本次会话的 [`Policy`](../../../native/session/download_plan.rs)；其他来源使用默认值。大小字段的单位为字节，文中 MiB 表示 1024 × 1024 字节。

| Header | `Policy` 字段 | 含义 | 默认值 |
|---|---|---|---|
| `Dfs-Max-Part-Bytes` | `maximum` | 分片模式的单片上限；整文件单流回退可以超过它 | 50MiB |
| `Dfs-Preferred-Part-Upper-Bytes` | `upper` | 均分大文件时的目标下界；也是合并组的硬上限 | 25MiB |
| `Dfs-Preferred-Part-Lower-Bytes` | `lower` | 小文件组包的目标大小 | 10MiB |
| `Dfs-Download-Concurrency` | `concurrency` | 本次下载会话的总在途数据请求数 | 16 |

三个大小字段作为一组生效：必须都能解析，且满足 `0 < lower <= upper <= maximum`，否则整组使用默认值。`maximum` 超过 256MiB 时三个值按 `256MiB / maximum` 等比例缩小；缩放后（或不需缩放时）`lower` 小于 1MiB 则整组使用默认值。并发建议独立解析，0 被忽略，上限 16。建议按会话固定，范围清单在创建 DFS2 会话之前形成，传输中不重新分片。

### 规划

[`plan_tasks`](../../../native/session/merge.rs) 先把不进规划器的文件留作单文件任务：内嵌完整文件、内嵌基文件加补丁、索引中找不到或长度为 0 的条目。其余文件以完整数据的索引范围和可选的补丁范围作为输入；补丁只在扫描得到的磁盘文件哈希与补丁基文件哈希一致时可用。

[`download_plan::plan`](../../../native/session/download_plan.rs) 的规则：

- 原文件大小不超过 1MiB（`SMALL_FILE`）的文件按完整数据的包内偏移排序后组包。组内的 TLV 头、未选中的数据及其他间隔都计入额外字节，额外字节不得超过请求范围的 20%。加入下一项会与上一项重叠、使范围超过 `upper`、违反 20% 约束，或使范围离 `lower` 比当前更远时，当前组结束；组范围达到 `lower` 时也结束。
- 组包后对相邻两组各做一次边界调整，不跨越重叠项。两组合计能在 `lower` 内合法合并时并为一组。否则在现有边界、两组中点、距起点 `lower`、距终点 `lower` 四个位置及其相邻一项的边界中选择：两组都不超过 `upper`、都满足 20% 约束、总传输字节不增加，并依次比较较小一组更大、较大一组更小、总字节更少。前缀统计在全部有序项上建立一次。
- 含有效补丁的完整数据组，另用"有补丁的项取补丁、其余取完整数据"重新组包；只有替代方案是单个请求且传输字节更少时采用替代方案，否则保留完整数据组。单独成组的小文件有有效补丁时使用补丁。
- 原文件大于 1MiB 的文件各自成为一个传输，有有效补丁时传输补丁。
- 选定后，长度不超过 `lower` 的单独补丁传输按偏移再组包一次，不做边界调整。
- 只含一个文件的传输按 `n = max(1, ceil(B / maximum), floor(B / upper))` 均分为 `n` 片，`B` 为压缩长度，各片相差最多一个字节；`n == 1` 时保持单请求。合并请求不切片，也不与大文件切片混在同一请求中。
- 相同压缩数据服务多个目标路径时，每个目标保留独立的生成与校验任务，可以重复读取同一范围。

`plan_tasks` 把只含一个文件的传输交给执行器时只保留文件本身；执行时 `build_install_op` 按本地、混合补丁、磁盘补丁、完整文件的顺序重新确定来源，[`resolve_install_source`](../../../native/session/run.rs) 用会话的 `Policy` 重新切片。合并传输携带成员、成员范围与整组范围。任务按原文件大小降序排列，较大的任务先开始。

### DFS2 申报与 URL 解析

[`dfs2_ranges`](../../../native/session/merge.rs) 申报合并范围、每个文件的完整范围及其切片、匹配的补丁范围和安装器前缀，排序去重后用于创建 DFS2 会话。

计划不保存 URL。每个数据请求先取得请求名额，再通过 `ipc::download::resolve` 请求范围 URL：直接模式经进程内通道，提权模式经管道发给会话。会话的 `resolve_in_windows` 把 50ms 内到达的请求合为一批，每来一个新请求重新计时，窗口结束时经批量接口一次取回；批量响应中单个范围失败只使该请求失败，整个批量请求失败则窗口内的请求全部失败。重试时重新解析 URL。范围响应核对状态码 206、`Content-Range` 与长度，响应体的长度由网络流核对（规则见 [UI 契约](./2026-09-02-ui-contract.md)的错误码一节），最终文件仍执行哈希校验。

### 调度

会话进程的 [`install_files`](../../../native/session/run.rs) 限制同时运行的逻辑任务：本地任务 16 个，大、小任务各取 `ipc::download::limits(concurrency)` 的两部分。`concurrency` 为 `N` 时大任务名额为 `clamp(floor(5N/16), 1, N-1)`，其余给小任务；`N == 1` 时两类各 1。任务按 `size_threshold` 分为大小两类：任务不超过 3 个时全部算大任务；否则把任务大小降序排列，取下标 `min(5, max(2, floor(3n/10)))`（从 0 起数）处大小的 80% 为分界，不小于分界的是大任务。合并请求算一个逻辑任务。只有纯本地读取的任务算本地任务，网络混合补丁占用网络名额。

执行进程（直接模式为本进程，提权时为 helper）的 [`download::Session`](../../../native/ipc/download.rs) 用同样的大小名额限制在途 HTTP 请求，`N == 1` 时两类共用一个信号量。名额覆盖 URL 解析、等待响应和读取响应体。一个任务的后续切片要等同一类中已开始的每个任务都拿到第一个请求后才能申请名额；之后按信号量的先到先得分配，两类之间不互相借用。

### 切片读取

[`sliced`](../../../native/ipc/download.rs) 按片序经一个容量为两块的通道向 Zstd 或补丁流供给数据，第一片直接从网络读取。读取每一片时，若磁盘预算能整块预留，就把其后最多两片预取到 `<staging>/dl/<uuid>.part`；没有预取的片在轮到时直接从网络读取。预取片收满声明长度后才可读，读完即删除并归还预算，不逐片 `sync_all`，不进入提交 journal。

每一片记下送来它的那次请求的 DFS insight，重新读取时以后一次为准。解码器拒绝数据时（`HASH_MISMATCH`），[`install_file.rs`](../../../native/ipc/install_file.rs) 按解码器停下的位置把码记在可能送来这段数据的片上：停下处之前 `UNDECODABLE_REACH`（两个 zstd 块加读缓冲，约 264KiB）以内的片。解码器读到数据末尾帧还没完，或文件的 hash 不符时，坏数据的位置无从推定，码记在每一片上。

磁盘预算在 `BeginDownload` 时确定：暂存所在卷的可用空间减去全部任务的原文件大小，上限 256MiB；查不到可用空间时取 256MiB。会话开始前的空间检查 `ensure_space` 只计入原文件大小。取消或失败时，执行器取消该文件的停止 token，唤醒等待中的读取方，等全部预取任务结束后再返回错误。

### 重试与回退

预取片最多尝试两次，每次重新解析 URL 并截断临时文件。流式读取的片在打开失败，或尚未收到任何字节就读取失败时重新打开一次。其余失败使本次安装操作失败，交给 [`install_one`](../../../native/session/run.rs) 的尝试循环：第一次按计划（补丁或切片）获取，第二、三次跳过补丁并以一个整文件请求获取，该请求可以超过 `maximum`。每次尝试重新解析节点；磁盘满、文件 IO 失败、权限不足和用户取消不重试。

合并请求在第一个成员完成之前失败时整组重试一次，重试仍失败则全部成员回退；之后的成员失败只记该成员。完成校验的成员保留，回退的成员各自经 `install_one` 跳过补丁、以整文件获取，最多两次。

### 提权分工与 IPC

私有 IPC 以会话为单位开启、取消和结束下载：`BeginDownload`（会话标识、并发、`dl\` 目录、预取预算）、`CancelDownload`、`EndDownload`；每个文件操作包在 `Download(Job, op)` 中执行，`Job` 指明会话与大小类别。范围 URL 请求与回复是管道上的独立消息，只传范围、URL、进度和结果，压缩数据与临时文件读取不经 IPC 转发。逻辑任务名额在会话进程，请求名额与磁盘预算在执行进程。

### 进度与诊断

UI 的文件总数和完成量按目标文件统计，切片不增加文件条目，每个目标文件只记一次完成。实际网络接收量按请求尝试累计，包含失败尝试、重试、合并间隔和整文件回退，读取临时切片不计入。日志 `download plan limits` 记录生效的 `Policy`、大小分界和两类名额；`File grouping result` 记录任务数、单文件任务数、合并组数、合并文件数、合并字节数与申报范围数；DFS2 申报的范围逐条记录。每个文件完成时记录一条，附带 DFS insight；insight 中的 URL 经 `sanitize_url_for_logging` 处理，不含签名参数。

## Alternatives considered

- 保留全部现有参数，仅让大文件自行开启多个请求：会使文件并发与切片并发相乘，无法保证文件间分配和服务端总预算。需要统一执行器。
- 对每个文件先固定最省字节的生成方式，再做合并：可能把连续全量组变成大量零散补丁请求。先比较小文件组的两类候选，再固定生成方案，可以保留减少请求的已有收益。
- 使用全局耗时成本模型选择所有补丁、全量、切片和组包组合：需要可靠的节点吞吐、建连和本地解码成本估计，且计算和维护成本较高。有界局部比较及代表性测量更适合作为起点。
- 客户端重新读取或补发 builder 的分类信息：包内已清除该字段，而实际偏移足以利用现有排列。增加包字段会扩大兼容性工作且不改善实际布局。
- 全部切片缓存于内存：节点速度不均时内存占用较高；严格背压又可能限制预取收益。固定落盘提供明确资源上限，第一片直供保留下载与解码重叠。
- 下载完整压缩文件后再解码：实现更简单，但第一片也要落盘，且解码不能及时开始。顺序流适配器保留现有解码器。
- 每个切片边接收边供给解码器并支持任意中途续传：可以减少落盘等待，但片级重试需要维护精确消费位置。只对未供给字节的片重试，已经供给的失败转整文件回退，失败状态更少。
- 引入 `multipart/byteranges` 响应：多个独立 Range 请求已经可以利用不同节点，不需要恢复[已移除的 multipart 解析器](./2026-08-28-drop-multipart-download.md)。
- 安装过程中持续接受新建议并重分片：增加范围申报、在途任务和临时数据处理的状态。会话开始时固定建议能先验证主要收益。

### 规划原型测量

规划阶段用未入库的 Python 原型比较参数。原型复现规划器之前的合并策略，并实现全量与补丁的局部比较、范围合并、尾组调整和均分切片；包读取部分只读扫描 TLV，逐项核对索引与物理偏移。基准区分真实包完整内容、真实版本清单差分和固定种子的合成选择集合。原型不含安装器自身映像生成、用户目录扫描、离线混合基文件、运行库、HTTP 执行和提权。下文"候选"指原型中的候选规划。输入包和实验输出只在本机，不入库，也不进 CI。

输入为三个生产包：下游应用甲的两个相邻版本（下称甲旧版、甲新版）与下游应用乙的一个版本。两个目标包分别含 1783、136 个应用文件，最大压缩数据项分别为 75,023,420、36,438,960 字节；超过 100MiB 的数据项使用合成样例覆盖。甲的清单差分含 135 个新增或变化文件，其中 115 个新增、2 个有匹配的补丁，假定旧版本文件完整且未被用户修改。

以下结果将目标包视为远端数据源，只统计应用数据请求，不包含元数据、节点解析、失败重试和运行库。候选使用 1MiB 小文件分类、10MiB 组包目标、25MiB 切片目标、50MiB 切片上限；两个补丁在真实更新的两种方案中均被使用。

| 输入 | 原策略请求数 | 候选请求数 | 原策略传输字节 | 候选传输字节 |
|---|---:|---:|---:|---:|
| 甲新版完整应用内容 | 83 | 67 | 471,165,813 | 469,463,221 |
| 乙完整应用内容 | 77 | 55 | 400,197,874 | 399,973,897 |
| 甲旧版 → 甲新版清单差分 | 24 | 17 | 152,307,451 | 152,307,818 |

这些是确定的范围与字节统计，不是实测下载加速比。真实布局的内存规划在 Windows 11 10.0.28000、Python 3.13.3 x64 下以 `perf_counter` 测量，每项重复 9 次，排除包解析、网络和磁盘读取，CPU 为 AMD Ryzen 9 7945HX with Radeon Graphics。候选规划中位数分别为 1.993ms、0.176ms、0.159ms，原策略的 Python 复现分别为 1.122ms、0.119ms、0.094ms。测量时没有 Rust 实现，这些时间不能用于预测 Rust 规划器的耗时。

规模测量使用固定种子生成小文件、间隔和三个大文件，输入在计时前生成，每项重复 5 次。1003、10003、100003 个目标的候选规划中位数分别为 0.762ms、11.311ms、145.871ms。另一次 `tracemalloc` 测得对应 Python 分配峰值约为 0.118MiB、1.543MiB、15.356MiB，排除输入对象和进程总内存。前缀统计采用标准库的定宽整数数组，数据关系与 Rust 向量实现接近；不为这些时间设置 CI 阈值。

原型的 9 项单测通过，包含 120 组固定种子的随机索引、多个参数组合、非零大偏移、重叠内容引用、补丁取舍、尾组均衡、不同文件优先获得名额，以及借用后的总并发和每文件并发上限。字节回放在三个真实输入上分别核对了 1729、83、123 个参与合并或切片的数据项，重组后的 SHA-256 与包内原始压缩字节一致；首片直接读取，后续片经本机缓存目录落盘。回放没有执行 Zstd 或补丁应用，不能代替传输、解码、取消和回退的执行器测试。

网络事件模型比较固定启动延迟、节点共享带宽和客户端带宽上限，并分别模拟节点轮转和按预计完成时间分配。模型没有 TCP、磁盘、解码、失败或预取背压，输出只作参数敏感性分析。15MiB、25MiB 组包目标和 10MiB 切片目标均未在所有模型中胜出；节点不均衡时部分方案反而更慢。默认值取 10MiB 组包和 25MiB 切片；没有真实 HTTP 测量，不据此宣称安装更快。

#### 25MiB 上限下的参数与调度参考

本节的模型时间是规划阶段的参考值，不作为回归阈值。25MiB 为模拟 CDN 范围大小约束的测试值，等于 26,214,400 字节，不是生产默认上限；实际服务端建议按字节传递，不能把 CDN 的十进制 MB 阈值直接当作 MiB。模型没有模拟缓存命中率。

输入共 12 组：上述三个真实完整内容或更新集合；以种子 17、71、173 从甲新版完整清单独立抽取约 20% 文件的三个稀疏更新集合；一万个小文件加 100MiB、110MiB、225MiB 大文件；单个 110MiB；五个 110MiB；100MiB、110MiB、225MiB、350MiB、40MiB、25.001MiB 混合；25MiB、50MiB 及两侧各 0.001MiB 的边界集合；一千个小文件加三个原始体积顺序与压缩体积顺序相反的大文件。合成文件只生成索引与大小，不分配对应内容。

三组扫描分别比较 19 个大小参数方案、20 个调度方案和 11 个带每文件并发限制的方案。大小参数包括 5MiB、10MiB、15MiB 合并目标，10MiB、15MiB、20MiB、25MiB 切片目标，0%、5%、10%、20% 额外字节比例，以及 0.5MiB、1MiB、2MiB、4MiB 合并资格上限，仅运行大小顺序合法的组合。调度比较固定 5/11 名额、借用空闲名额、按压缩传输量排序、按剩余未派发字节选择额外切片，以及每文件 2、3、4、5 个在途请求的限制。

在生产包原布局上，只把客户端合并资格从 1MiB 提高到 2MiB，使三个真实输入的请求数从 69、57、18 降至 64、55、17，传输分别增加 210、84、42 字节。该实验没有调整生成器分类，只反映现有布局中的相邻文件合并。例如甲更新额外合并的两个文件原始体积约为 1.603MiB 和 1.024MiB，它们在现有大文件区域已相邻，中间只有 42 字节 TLV 头部；这个收益不能代表按更新状态重排后的效果。

25MiB 上限、25MiB 和 15MiB 目标分别对三个真实输入执行压缩字节回放，全部 SHA-256 校验通过。两种目标分别核对 1730、85、123 个参与合并或切片的数据项。25MiB 目标的后续片临时写入量为 66,499,907、31,494,763、50,015,613 字节；15MiB 目标为 72,751,859、31,494,763、56,267,565 字节。这是累计写入量，不是磁盘峰值；较小首片让更多字节经过临时文件。回放未验证解码速度、HTTP 失败或预取背压。

据此默认切片目标为 25MiB，10MiB、15MiB 留作服务端建议的比较值。借用空闲名额在模型中改善的组合最多，但没有经过受控传输验证，执行器不借用；每文件除当前片外最多预取两片，不按可用字节放宽。

#### 生成器与客户端同时采用 2MiB 的参考

布局模拟按生成器的大文件、未变化小文件、变化或新增小文件、小补丁、大补丁五类及名称排序，只重新计算索引偏移。应用文件按原始体积分组，补丁按 metadata 中未压缩补丁的大小分组；保留现有压缩长度、共享 payload 去重、TLV 头部、补丁集合和固定前缀。将分类阈值从 1MiB 改为 2MiB，不改变生成补丁时跳过小于 1MiB 文件的既有规则，也不重新生成或压缩内容。完整安装的规划输入与生成包时采用的更新基准分别传入，避免把完整安装误当作首次生成包。

以甲旧版作为生成甲新版的唯一旧版本基准时，模拟的 1MiB 分类精确复现原包 1779 个数据项的全部偏移。对共享内容使用与生成器相同的按 hash 判断变化规则；布局单测覆盖应用文件与补丁的分类依据、同一内容对应多个路径和重复重排的稳定性，布局模拟加原有规划测试共 11 项通过。

乙缺少旧版本，因此两个虚拟布局均假定全部文件为新增；1MiB 虚拟布局有 78 个数据项偏移与生产包不同，只能作为该假设下的完整安装比较。另用三个种子在甲新版的真实清单上构造约 20% 变化的旧版本，及三个含 1000 个文件的合成版本对：70% 文件从 1KiB～1MiB 取样，25% 从大于 1MiB～2MiB 取样，5% 从大于 2MiB～5MiB 取样，压缩长度为原始长度的 20%～90%；更新文件独立抽取约 20%。这些构造更新没有生成补丁。每组均比较原布局、1MiB 虚拟布局和 2MiB 虚拟布局，以及两种客户端资格上限。

## Consequences

- 切片落盘增加压缩字节的一次磁盘写入和读取，在机械硬盘或磁盘已饱和的设备上可能抵消网络并行收益。顺序解码可能被靠前的慢切片阻塞；执行器不发重复竞速请求，网络足够快而解码受限时，增加切片不会继续提速。
- 小文件取舍偏向减少请求，不能保证每个网络环境下最短耗时。服务端建议在一次安装中可能过时；这些影响只是性能退化，不改变文件内容、提交安全性或成功判定。
- 执行器不持有不可变计划：单文件任务在执行时重新确定来源并重新切片，与规划时的选择一致依赖两处使用同一 `Policy` 与同一判定顺序。
- 重试仍分散在两处：合并请求的嵌套重试，和 `install_one` 最多三次的尝试循环；没有统一的有界重试状态。
- IPC 以会话为单位开关下载、逐个文件包装操作；范围 URL 请求不带计划或批次标识。逻辑任务名额与请求名额分处会话进程和执行进程。
- 名额分配只有"先给每个任务第一个请求"一条公平规则，其余按信号量先到先得，没有优先解码器当前所需范围、也没有按文件轮转。`concurrency` 为 1 时请求名额只有一个，会话侧仍可同时运行一个大任务和一个小任务。
- 空间检查只计入原文件大小，预取预算取剩余空间且不超过 256MiB；256MiB 是否足够没有测量。
- 长度不超过 `lower` 的补丁都参与补丁再组包，包括原文件大于 1MiB 的补丁，再组包不做边界调整。
- 诊断日志没有切片数量、合并额外字节和预计压缩字节，也没有记录实际请求数、回退次数和预取峰值的执行摘要。
- e2e 不覆盖切片、片级重试与整文件回退，这些路径只有上表列出的单测；与规划器之前实现的性能对照和 release 体积影响没有测量。
