# 类型统一：IPC 链路去 Value，元数据镜像合一

Status: implemented

## Problem

两处同源问题：同一形状在代码里有两个表示，以及跨进程/跨模块传递时退化成 `serde_json::Value` 再猜回来。

### IPC 链路

请求方向已类型化：`IpcInner{op,id}` → `to_vec` → 管道 → `from_str::<IpcInner>`。响应与进度方向仍全部经由 Value。

- UAC 侧每个操作的类型化结果被 `json!`/`to_value` 打成 Value（`src/ipc/operation.rs` 15 个 arm、`src/ipc/install_file.rs` 3 处），再塞进 `json!({"id","data","done"})` 信封上管道；主进程 `handle_pipe` 逐行 `from_str::<Value>`，按 `envelope`/`breadcrumb`/`id` 三个 key 探测路由；消费端再 `from_value::<T>` 转回类型。
- 未提权路径在同一进程内走完 typed → Value → from_value 整圈：序列化代码全付，零字节上管道。
- 每个结果类型因此付出 `to_value` 与 `from_value` 两份单态化副本，每份 2–6KiB（`cargo bloat`，本机 x86_64-pc-windows-msvc、opt-level=s + LTO、非 build-std）。
- Value 探测带来一层形状猜测代码：`unwrap_ipc`（session/run.rs）兼容 `{"Err":字符串}` 与 `{"Err":{message}}` 两种形状；`take_insight` 依次试 `insight`、`/Ok/insight`、`/Err/insight` 三条 JSON pointer；`apply_ipc_progress` 用 `get("chunk_index")`→`as_u64`→`as_array` 三连猜还原进度；`scan_progress_pair` 从数组位置猜二元组。另有四处消费端手扒：check_local_files（26 行逐字段 `get()`+`as_str()`）、install_merged（`get("results")` 后逐项试 `get("Err")`/`get("error")`）、ProbeWritable（`as_array`+`as_str` 拼 `Vec<String>`）、RunMirrorcInstall。
- 进度事件形状彼此不一致且带无人读取的字段：multichunk 信封的 `chunk_range` 无任何消费端读取，mirrorc 事件靠 `"type"` 字符串自述类型，`apply_ipc_progress` 保留着无生产者命中的 `payload` 兜底与 `as_array` 分支。原始进度不到达 webview——全部先在 Rust 侧解释聚合再走 SessionUi，形状不受前端约束。
- `mgr.run()` 两条路径返回形状不一致：未提权路径返回裸 Value，提权路径返回仍包着 serde 外部标签的 `{"Ok":…}`/`{"Err":…}`，由 `unwrap_ipc` 事后擦平。正常结果若是含 `"Ok"`/`"Err"` 键的对象，本地路径会被误解包；当时的结果形状恰好都不含这两个键。

### 元数据镜像

`.metadata.json` 这一个 JSON schema 在代码里有两套 Rust 镜像，五对类型：

| 写向 `utils/metadata.rs` | 读向 `session/{types,plan}.rs` | 差异 |
|---|---|---|
| `RepoMetadata` | `DfsMetadata` | 多 `repo_name`、`assets`、`packing_info`；`Option<Vec<_>>` vs `Vec<_>` |
| `Metadata` | `HashInfo` | 多 `installer: Option<bool>` |
| `PatchInfo` | `PatchInfo`（同名） | 仅 `from`/`to` 的元素类型 |
| `PatchItem` | `PatchSide` | 仅 `#[serde(default)]` |
| `InstallerInfo` | `InstallerMeta` | 无，字段与类型完全一致 |

写向由 `builder/gen.rs` 构造并 `to_string` 写出，`builder/{pack,extract}.rs` 读回；`utils/metadata.rs` 经 `src/builder/utils/mod.rs` 的 `#[path = "../../utils/metadata.rs"]` 共享给 kachina-builder binary。读向由 `session/source.rs` 从网络解析，挂着 `hash_key`/`item_hash` 等安装器侧方法。schema 每变一次要改两处。

差异都不是有意的设计边界：

- `assets` 是死字段——`gen.rs` 只写 `None`，全仓库无 reader。
- `repo_name`、`packing_info` 只有 builder 读写；`pack` 在嵌入前剥掉 `packing_info`。
- `HashInfo.installer` 不经 wire：由 `session/run.rs` 进程内合成（把 updater exe 塞进 `latest.hashed` 并打 `Some(true)`），`merge.rs`、`run.rs` 读来算 `0-installer_end` 字节范围；`gen.rs` 反而主动把 updater 从 hashed 里剔掉。写向没有这个字段是对的。
- `Option<Vec<_>>` 与 `Vec<_>` 的分歧来自序列化方向：写向要 `skip_serializing_if` 让输出最小，读向要 `serde(default)` 容忍缺席。两者可以同时挂在一个 `Vec` 字段上，不构成冲突。全仓库对这些字段的读取都是取到后直接迭代，没有一处区分 `None` 与 `Some(vec![])`。

两套镜像之间靠 JSON round-trip 互转，两处：嵌入元数据 `config.enbedded_metadata` 与 mirrorc 安装结果，都是 `from_value::<DfsMetadata>(v.clone()).ok()`。后者是有条件的静默失败：`run_mirrorc_install` 真实返回 `(Option<RepoMetadata>, Option<MirrorcChangeset>)`，消费端当数组取首元素；写向 `hashed` 带 `skip_serializing_if` 可以缺席，而 `DfsMetadata.hashed` 是无 `default` 的裸 `Vec`，字段缺席则整体反序列化失败并被 `.ok()` 吞成 `None`，元数据无声丢失。

## Decision

`.metadata.json` 只有一套 Rust 定义，放在 `src/utils/metadata.rs`（builder 经 `#[path]` 共享）。名字是 `RepoMetadata` / `FileMeta` / `PatchInfo` / `PatchSide` / `InstallerInfo`。没有 `DfsMetadata` 别名。

```rust
pub struct RepoMetadata {
    pub tag_name: String,
    pub hashed: Vec<FileMeta>,                              // 必填
    #[serde(default, skip_serializing_if = "Vec::is_empty")]
    pub patches: Vec<PatchInfo>,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub installer: Option<InstallerInfo>,
    #[serde(default, skip_serializing_if = "Vec::is_empty")]
    pub deletes: Vec<String>,
    #[serde(default, skip_serializing_if = "String::is_empty")]
    pub repo_name: String,
    #[serde(default, skip_serializing_if = "Vec::is_empty")]
    pub packing_info: Vec<Vec<String>>,
}
```

`hashed` 不加 `#[serde(default)]`：缺字段即解析失败。本仓库 builder 无条件写出该字段；缺 `hashed` 的第三方元数据不能再静默当成「无元数据」。`assets` 不存在，未知字段按 serde 默认忽略。空 `Vec` 写出时省略、读入缺席当空。`FileMeta.installer` 由 `session/run.rs` 进程内合成、`skip_serializing_if = "Option::is_none"`，任何写出路径都不填。

`.metadata.json` 的解析入口统一走 `serde_json::from_str`，包括嵌入包里的 `\0META`。serde 的反序列化代码按 `Deserializer` 类型单态化，多用一种读取器就多一整棵副本。

`hash_key` / `item_hash` 留在 `session/types.rs` 的 `impl RepoMetadata`。`utils/metadata.rs` 被 builder 用 `#[path]` 编进 `kachina-builder`，builder 没有 `session` 模块。

IPC 进度与结果在 `src/ipc/mod.rs`：`Progress`（六变体）、`IpcResult`（与 `IpcOperation` 一一对应）、`IpcError { message, insight }`、`PipeMsg`。标签风格与 `IpcOperation` 相同，外部标签（见 [IPC 外部标签改造](./2026-08-28-ipc-external-tagging.md)）。`run_opr` 与 `mgr.run()` 都返回 `TAResult<IpcResult>`；未提权路径进程内直调，不经序列化。

`ProgressNotify` 是 `Fn(Progress)`。生产端是 `fs.rs`（`CountOf`）、`install_file.rs`（`Bytes` / `Chunk`）、`runtimes.rs` 与 `mirrorc.rs`（`BytesOf` / `Extract` / `Delete`）。消费端 `apply_ipc_progress` match `Chunk` / `Bytes`；runtime 仍用 `cur + 1 < total` 区分下载/安装文案。

`IpcError::from_ta` 先 `to_value(&TACommandError)`，让 capture-on-serialize 钩子跑完（UAC 侧 `is_pipe_mode()` 拦截上报），再组 `{message, insight}`。主进程 `into_ta()`。`IpcResult::insight()` 只读 `InstallFile` / `InstallMultichunkStream` 上的具名字段，不是按变体拆包的提取层。调用方用 `let-else` + `bail!("IPC_SHAPE_ERR")` 拆 `IpcResult`。`FindProcessByName` 操作失败仍当空列表；变体不对才 `IPC_SHAPE_ERR`。

`PipeMsg`：`Progress` / `Ok` / `Err` 进操作广播；`Envelope` / `Breadcrumb` 只交 sentry；`Disconnect` 只走进程内广播。sentry `pipe_send` 发 `PipeMsg::Envelope` / `Breadcrumb`。

变体形状按「编译器能不能查出位置写反」定：字段异型或只有一个字段时用元组变体，同型多字段保留具名。serde 为每个具名字段变体生成的样板按变体计（≈1,024 字节/变体），单字段变体性价比最差且变体名已经说明了那个字段是什么。

插件回复、注册表 `InstallerMeta` 这类「拿到一段 JSON 文本、各消费端解成不同类型」的链路全程传 `String`，不在中途落成 `Value`：反序列化按 `Deserializer` 类型单态化，经 Value 中转会为每个目标类型多留一整棵副本。

`pack` 嵌入元数据走 `embed_metadata_bytes`：清空 `packing_info`，`json!` 后再 `sort_all_objects`。`packing_info` 为空不参与文件分类排序。`gen` 写出的 `.metadata.json` 字段序与空数组是否落盘不是约束。管道两端是同一 exe，wire 形状无跨版本兼容义务。

## Alternatives considered

- **只做 IPC 类型化，镜像留两套。** RunMirrorcInstall 变体需先写 `RepoMetadata → DfsMetadata` 转换函数，镜像合一时再删；schema 的双写维护成本不变。
- **只合并镜像，IPC 保持 Value。** 消除双写与两处 round-trip，但 Value 侧单态化副本与形状猜测代码原样保留。
- **合并时保留 `pub use ... as DfsMetadata` 别名过渡。** 安装器侧引用零改动，但两个名字继续并存，读者仍需判断二者是否同物。
- **给 `hashed` 加 `#[serde(default)]`。** 缺字段时不再报错，但 DFS 路径也随之对残缺元数据变宽容，安装器会拿着空文件列表跑完全流程。
- **进度枚举照搬当时的 6 种形状。** 当时形状裸数字、二元组、带 `"type"` 标签的对象混杂，照搬等于把不一致固化进类型。按语义归一后同为 6 变体，且 `chunk_range`、`payload`、`as_array` 三处死代码随之清除。
- **为 `IpcResult` 造一层提取方法**（`fn check_local_files(self) -> Result<…>` 等）。调用处少一行，但 impl 块本身即十余个小函数的样板，样板总量不变。
- **保持 Value，仅修 `mgr.run()` 的形状不对称。** 消除误解包隐患但不减体积，单态化副本与探测代码原样保留。
- **进程内路径特判跳过序列化，管道路径保持 Value。** 体积由单态化副本的存在决定，提权路径不改则副本全在，收益趋零。
- **把同型多字段变体也元组化。** `BytesOf`/`CountOf`/`Extract`、`RunMirrorcInstall`、`HybridPatch` 各能再省 ≈1KiB，但字段同型，位置写反编译器发现不了，只会在运行时把进度分母当分子、把源路径当目标路径。省的是字节，赔的是类型化本来要买的东西。
- **对 `PipeMsg` 的解析点加 `#[inline(never)]`。** 假设是 `visit_enum<…StrRead>` 与 `handle_pipe::async_block$0` 两个符号字节数相同（各 10,650）意味着 LTO 复制了一份反序列化器。实测 3,921,920 → 3,921,920，一字节没变：字节数相同是巧合。
- **`ManagedElevate::run` 里 `Box::pin(run_opr(...))`。** 假设是 `run` 的 16,691 字节主要来自内联 future 的 drop glue。实测 +1,024，更差。
- **只在 `apply_plugin_metadata` 里加 `to_string` 转接**，不动插件回复的类型。改动面小，但只是把 Value 挪到门口——`PluginResult::Value(Value)` 那棵树仍要为每个消费端各建一次。全链路传字符串多省 4.5KiB。
- **卸载路径直接 `from_str::<RepoMetadata>`**，不另立 `UninstallMeta`。少一个类型，但 `tag_name`/`hashed` 必填会让缺字段的旧注册表项直接卸载失败。

## Consequences

- 缺 `hashed` 的元数据在 mirrorc / DFS 解析时报错，不再静默当成「无元数据」。本仓库 builder 总写该字段；第三方线上形状无法在本地核实。
- 空 `repo_name` 在嵌入 JSON 里被省略（`skip_serializing_if = "String::is_empty"`）。合并前的写出镜像无条件写出 `"repo_name":""`。`gen --repo` 的常规输入带非空名字，对照用例覆盖的是这一类。
- `BytesOf` 与 `CountOf` 字段相同，选错变体只错进度文案，编译能过。
- `FileMeta.installer` 与 wire 字段同形；builder 若填写它，安装器会把该条目当成安装器自身。
- `TACommandError` 的上报仍绑在 `Serialize` 上。新位置若再序列化一次错误，就多一次 Sentry 事件。`IpcError::from_ta` 依赖这次序列化触发钩子。
- sentry 管道通道没有单测；形状不一致时提权进程的 panic 上报与面包屑会无声消失，安装不会因此失败。
- 只做类型化、不做后两条去 Value 时，`.text` 净 +15.9KiB（文件 3,926,016），按符号对照基线分组：IPC 枚举的 serde 派生 +33.4KiB（`PipeMsg` / `IpcResult` / `Progress` / `IpcError`，基线为 0），`ipc::manager` +17.4KiB（`handle_pipe` / `run` / `uac_ipc_main` 改成匹配具名变体），mirrorc −10.5KiB，元数据镜像合一 −6.4KiB，`session::run` −3.3KiB。最大的两个符号 `run_opr`（63,386 → 63,488）与 `IpcOperation` 反序列化（33,382 → 33,280）基线上就是这个体积，与类型化无关。这 +15.9KiB 由下面的变体元组化与全链路传字符串两条抵过并倒赚。
- **serde 的具名字段变体样板按变体计，不按字段计**，实测 ≈1,024 字节/变体：每个具名字段变体各生成一套 `__Field` 枚举、`visit_str` 字符串匹配器、逐字段 `Option` 跟踪与缺字段错误路径。所以单字段具名变体的性价比最差，而改成元组变体零可读性损失——变体名已经说明了那唯一一个字段是什么。转换的判据是**编译器可查**：字段异型时位置写反编译不过（`Progress::Chunk(u32, u64)` 合格），同型字段必须保留具名（`BytesOf`/`CountOf`/`Extract`、`RunMirrorcInstall{zip_path,target_path}`、`HybridPatch{diff,source}`——写反不会被发现）。据此转了 `PipeMsg` 前三个信封变体、`IpcOperation` 的 4 个单字段变体、`InstallFileMode::Direct`、`Progress::Chunk`，共 −12,288 字节，把类型化的净成本从 +16,896 压到 +4,608（对照基准是「只做 `\0META` 的 `from_str` 归一、不做类型化」的反事实构建 3,909,120）。
- 反序列化代码按 `Deserializer` 类型单态化，同一个类型每多一种读取器就多一整棵副本。`RepoMetadata` 一度同时挂着 StrRead、SliceRead、Value 三棵，合计约 53KiB。SliceRead 那棵随 `\0META` 改 `from_str` 消失（3,954,688 → 3,926,016）。Value 那棵靠**全链路传字符串**收掉：插件回复不解成 `Value` 再 `from_value`，`PluginResult::Value(String)` 直接携带原始 JSON 文本，消费端各自 `from_str` 成自己的类型（`Dfs2Data` / `PluginChunkUrl`）；`Dfs2Data.metadata` 与 `InstallerConfig.enbedded_metadata` 同时改成类型。−19,968 字节，其中一部分来自顺带消掉的 `Dfs2Data` 自己的 Value 树和 `get("url")`/`as_str` 探测。代价是前端 `src/plugins/bridge.ts` 的 `answer({data})` 改发 `JSON.stringify(...)` 字符串，Rust 侧 `PluginAnswer.data` 为 `Option<String>`——**JS 与 Rust 的这条契约必须同版本部署**。
- 卸载路径同法：`read_uninstall_metadata_raw` 返回注册表 `InstallerMeta` 的原始文本（只用 `IgnoredAny` 校验是合法 JSON，不建树），调用方 `from_str` 一次。这里没有直接解 `RepoMetadata` 而是用了窄投影 `UninstallMeta { hashed, deletes }`：`RepoMetadata.tag_name`/`hashed` 是必填的，缺字段即整体报错，而卸载是最不该硬失败的路径。−2,560 字节。行为上有一处收窄：`hashed` 里单条元素解析失败会让整个 `hashed` 落空（`unwrap_or_default`），而不是像逐条 `filter_map(...ok())` 那样只跳过坏的那条——`FileMeta` 只有 `file_name`/`size` 必填，所有写出路径都填。CI `uninstall` e2e 覆盖这条路径：安装 v1 后跑静默卸载，断言 `hashed` + `deletes` 列出的文件被删、`User/` 下运行期数据保留。
